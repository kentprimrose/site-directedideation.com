# Plan: move the authenticated pilot to `mcp.directedideation.com`

Repository review; live infrastructure, DNS, certificates, and WorkOS were not inspected. The local test suite passed: 188 tests. This is regression evidence, not proof of live routing, OAuth interoperability, or production security.

## Recommendation and scope

The shortest safe path is to move the existing authenticated, invite-only pilot to `https://mcp.directedideation.com/mcp`, retaining its current WorkOS staging environment and subject allowlist. This is a **pilot hostname migration, not a general production launch**. A second backend, dual-host support, a new authentication system, and subscription infrastructure are not necessary for this limited move.

There is an approval discrepancy to resolve first: `PLAN.md` calls for legal review, independent security review, and disclosures before the invite-only pilot, while `staging_mcp/DEPLOYMENT.md` describes an active pilot with accepted residual risks. Confirm whether the original gates were satisfied or explicitly waived for the existing pilot; changing the hostname does not resolve that discrepancy.

## Findings

1. **Do not expose the wrong service.** The authenticated pilot listens on loopback port `8765`; the separate service on `8001` is unauthenticated and must remain private. Routing the new hostname to `8001` would bypass the pilot's access controls. See `staging_mcp/compose.yaml` and `deploy/README.md`.
2. **This is a coordinated cutover, not a DNS rename.** The configured hostname determines the accepted Host, protected-resource metadata, token audience, and health check. Only one hostname and audience are accepted at a time, so existing clients must switch URLs and obtain new tokens. A brief scheduled interruption is simpler than adding dual-host support. See `staging_mcp/server.py` and `staging_mcp/DEPLOYMENT.md`.
3. **Proxy and rollback work are the main operational gaps.** Existing nginx, certificate, and HTTP-01 examples refer to the staging hostname. The documented rollback tooling recognizes specific configuration hashes; modifying its protected file without an updated, verified recovery procedure can make emergency rollback refuse to run. Parallel nginx configs also need careful handling of default listeners and rate-limit zone names. See `docs/PROD_DEPLOY_GEMINI.md` and `staging_mcp/DEPLOYMENT.md`.
4. **The earlier review documents contain stale state claims.** Both production-review documents describe relevant work as uncommitted. At this review, the working tree was clean and local `main` was five commits ahead of `origin/main`. That does not establish what is deployed; compare the running image and installed files before changes. Pushing `main` can trigger the separate private-service deployment; it does not deploy this pilot. See `.github/workflows/private-deploy.yml`.
5. **A clean URL does not make this general production.** The pilot uses a WorkOS staging issuer, a small subject allowlist, and limited client/security evidence. Broader launch gates include production identity configuration, legal and privacy work, independent security review, token-semantics and client testing, and operational readiness. Account persistence and billing need not be implemented merely to rename the pilot.

## Shortest safe sequence

1. **Confirm scope and inventory the live state.** Verify the intended limited-pilot use, applicable approvals, running image and Compose inputs, installed nginx configuration and rollback script, current DNS, firewall, certificate renewal, and WorkOS configuration. Preserve and independently verify known-good rollback artifacts. Do not assume the IP or live hashes in the plans are still current.
2. **Prepare the new hostname without disturbing staging.** Review a separate new-host nginx/TLS configuration and certificate issuance and renewal procedure. Check the complete shared nginx configuration, including listener defaults, rate-limit zones, IPv4/IPv6, and inherited logging. Prepare and rehearse a rollback that covers the new configuration; avoid overwriting hash-pinned artifacts blindly.
3. **Provision DNS, certificate, and WorkOS resource.** Point the new name to the verified host; ensure AAAA behavior matches the reviewed IPv6 exposure. Obtain and verify the certificate and renewal path. Register the exact new resource `https://mcp.directedideation.com/mcp` in the **existing staging** WorkOS environment, retaining the old resource for rollback.
4. **Cut over in an agreed window.** Under the staging-operation lock documented in `staging_mcp/DEPLOYMENT.md`, deploy the reviewed image and configuration with `STAGING_MCP_HOST=mcp.directedideation.com`, preserving the issuer and current allowlist. Activate the reviewed proxy configuration. Tell pilot users to update their client URL and reauthorize.
5. **Verify externally and roll back on failure.** Check certificate and DNS, private backend exposure, metadata and issuer/resource, unauthenticated and unauthorized rejection, old-audience rejection, Host/SNI handling, rate-limit behavior, and a real authorized client's discovery, reauthorization, `ping`, and guidance call. Confirm unrelated hosted services still work. Rollback must restore the **old image, hostname environment, proxy configuration, and routing**, not merely retag an image; then verify the old endpoint end to end.

The next action is a **read-only live inventory and reconciliation of the pilot approval/gate discrepancy**, followed by preparation of the new-host proxy and a tested rollback procedure. Live changes require separate authorization.
