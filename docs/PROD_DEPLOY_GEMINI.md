# Production Evaluation and Shortest Safe Path to `mcp.directedideation.com`

## 1. Project & Architecture Review

The repository currently maintains two distinct service tracks alongside the static field guide (`site/public/`):

1. **Unauthenticated Private Prototype (`127.0.0.1:8001`):**
   - Defined in root `compose.yaml`, `Dockerfile`, and `src/site_directedideation_com/mcp/__init__.py`.
   - Auto-deployed on pushes to `main` via `.github/workflows/private-deploy.yml` into `/opt/directed-ideation`.
   - Includes SQLite aggregate telemetry (`METRICS_DB=/metrics/metrics.sqlite3`), has **no authentication**, and is strictly loopback-only.

2. **Authenticated Public Pilot / Staging Service (`127.0.0.1:8765` behind shared Nginx `:443`):**
   - Defined in `staging_mcp/server.py`, `staging_mcp/compose.yaml`, and `staging_mcp/Dockerfile`, using an isolated build context generated by `scripts/prepare_staging_build_context.py`.
   - Imports the exact same 4 canonical guidance tools and `INTERVIEW_STAGES` from `src/site_directedideation_com/mcp/__init__.py` (plus `ping`), without invoking the SQLite metrics lifespan.
   - Enforces WorkOS RS256 JWT verification (`StagingVerifier`) with strict issuer/audience/subject allowlisting, 64 KiB request body limits (`MCPBodyLimitMiddleware`), non-echoing argument validation (`ToolInputBoundary`), `TrustedHostMiddleware`, and container hardening (`read_only`, `cap_drop: ALL`, `no-new-privileges`, `10001:10001`, memory/CPU/PID limits).

## 2. Evaluation of the Production & Hostname Migration Plan

`PLAN.md` and `staging_mcp/DEPLOYMENT.md` wisely separate **two different milestones**:

1. **Moving the deployed authenticated pilot to the non-staging URL (`https://mcp.directedideation.com/mcp`):**
   - Kept strictly as the **invite-only, allowlisted US pilot** using the existing hardened `staging_mcp` container and WorkOS AuthKit + `WORKOS_STAGING_ALLOWED_SUBJECTS` allowlist.
   - **Never expose port `8001` (`directed-ideation` private service)** to `mcp.directedideation.com`—it has no auth or rate limits.
2. **General Production Launch (Broad / Self-Serve / Commercial Availability):**
   - Appropriately **blocked** in `PLAN.md` on:
     - Switching from a WorkOS Staging environment to a **WorkOS Production environment** (`WORKOS_STAGING_ISSUER` is just an env var name in `staging_mcp` and can hold any canonical HTTPS issuer origin, though renaming or aliasing it later is cleaner).
     - Legal review and publishing the plain-language privacy/security & subprocessor disclosures on the site before user signup.
     - Independent security review / penetration testing.
     - Interactive client validation across Claude chat, ChatGPT, and Codex against the remote endpoint.
     - Account/team/subscription persistence (note: `docs/AUTH_FOUNDATION.md` describes an internal password/Argon2id auth library that is not wired to HTTP/MCP and overlaps with WorkOS AuthKit—keep WorkOS AuthKit as the canonical OAuth provider per `PLAN.md` rather than maintaining dual auth stacks).

## 3. Critical Findings in the Current Cutover Plan (`staging_mcp/DEPLOYMENT.md`)

Reviewing `staging_mcp/DEPLOYMENT.md` against the codebase and helper scripts reveals **three important operational traps** to avoid during the URL move:

1. **Single-Host / Single-Audience Pinning (Hard Cutover):**
   - In `staging_mcp/server.py`, setting `STAGING_MCP_HOST=mcp.directedideation.com` simultaneously switches:
     - `TrustedHostMiddleware` (`allowed_hosts=[host]`)
     - OAuth Protected Resource Metadata (`/.well-known/oauth-protected-resource/mcp` -> `resource: https://mcp.directedideation.com/mcp`)
     - `StagingVerifier` expected JWT `aud` (`https://mcp.directedideation.com/mcp`)
     - Container `healthcheck.py` `Host` header
   - Because only one hostname is accepted at a time, switching the backend container immediately invalidates `mcp-staging.directedideation.com` requests and tokens.
   - **Recommendation:** Pre-provision DNS and TLS for `mcp.directedideation.com` and register the WorkOS resource indicator **before** touching the running container, so the actual cutover is a single sub-minute container recreate + Nginx reload.

2. **Hash-Pinned Rollback Script Trap (`di-shared-test-rollback`):**
   - `staging_mcp/shared-nginx-test/di-shared-test` refuses to roll back `/etc/nginx/conf.d/di-staging-public-test.conf` unless its SHA-256 matches `7f840890...` or `814b89c8...` (both of which hardcode `mcp-staging.directedideation.com`).
   - If you edit `/etc/nginx/conf.d/di-staging-public-test.conf` in place to change `server_name` to `mcp.directedideation.com`, **the emergency rollback script `/usr/local/sbin/di-shared-test-rollback` will fail with `unexpected public configuration; manual intervention required`**.
   - **Shortest Safe Fix:** Either (a) keep `di-staging-public-test.conf` untouched or rolled back cleanly via `di-shared-test-rollback`, and install a dedicated `/etc/nginx/conf.d/di-mcp-pilot.conf` for `mcp.directedideation.com` (removing `default_server` from the old file if both exist simultaneously), or (b) update the expected digest in `di-shared-test` alongside the new config using the same atomic pattern as `adjust-live-rate.sh`.

3. **Shared Rate-Limit Zone Names in Nginx:**
   - `staging_mcp/nginx.conf.example` defines `limit_req_zone ... zone=staging_mcp_req:10m` and `limit_conn_zone ... zone=staging_mcp_conn:10m`.
   - If a new Nginx config file is loaded alongside `di-staging-public-test.conf` during testing, reusing the exact same zone names in `limit_req_zone` will cause `nginx -t` to fail with a duplicate zone definition error. Use distinct zone names (e.g., `pilot_mcp_req` and `pilot_mcp_conn`) or replace the staging server block cleanly.

## 4. Shortest Safe Path to Move the Deployed Version to `https://mcp.directedideation.com/mcp`

Because the uncommitted code in the working tree already implements and tests `STAGING_MCP_HOST=mcp.directedideation.com`, no new application features are needed to move the deployed pilot to `mcp.directedideation.com`.

### Phase A: Pre-Cutover Preparation (Zero Downtime — Current Staging Keeps Running)

1. **DNS:**
   - Create the `A` record for `mcp.directedideation.com -> 138.197.24.16` (and verify no `AAAA` record exists, matching the IPv4-only Nginx listener policy).
   - Verify propagation externally (`dig +short A mcp.directedideation.com`).

2. **WorkOS Resource Registration:**
   - In the WorkOS dashboard, add `https://mcp.directedideation.com/mcp` as an allowed MCP Resource Indicator (keep `https://mcp-staging.directedideation.com/mcp` registered until cutover is verified so rollback remains instant).

3. **ACME HTTP-01 & TLS Certificate Issuance:**
   - Add an HTTP-01 server block on port 80 for `mcp.directedideation.com` serving `/.well-known/acme-challenge/` from `/var/lib/di-staging-acme` (adapted from `staging_mcp/nginx-http01.conf.example`), test with `sudo nginx -t`, and reload Nginx.
   - Issue the certificate without letting Certbot rewrite Nginx:
     ```bash
     sudo certbot certonly --webroot -w /var/lib/di-staging-acme \
       -d mcp.directedideation.com --email YOUR-EMAIL --agree-tos
     ```
   - Update or add a renewal deploy hook in `/etc/letsencrypt/renewal-hooks/deploy/` for `/etc/letsencrypt/live/mcp.directedideation.com` so renewals run `nginx -t && systemctl reload nginx`.

### Phase B: Build & Stage on the Droplet

4. **Sync Reviewed Files to the Droplet:**
   - Transfer the updated `staging_mcp/`, `scripts/prepare_staging_build_context.py`, and `src/site_directedideation_com/` files to the droplet checkout (and install the reviewed `staging_mcp/compose.yaml` to `/etc/di-staging/compose.yaml` if using `add-allowed-user.sh`).

5. **Tag Rollback Image & Build New Image (Under Lock):**
   - Acquire `/run/lock/di-staging-allowlist.lock`:
     ```bash
     sudo docker image tag directed-ideation-staging-mcp:local directed-ideation-staging-mcp:rollback
     python3 scripts/prepare_staging_build_context.py
     sudo docker compose -p di-staging -f /etc/di-staging/compose.yaml build
     ```

### Phase C: Atomic Cutover & Verification (~30 Seconds)

6. **Switch Container to `mcp.directedideation.com`:**
   - Recreate `di-staging` with `STAGING_MCP_HOST=mcp.directedideation.com` (preserving `WORKOS_STAGING_ISSUER` and `WORKOS_STAGING_ALLOWED_SUBJECTS`).
   - Verify container health (`docker compose -p di-staging ps` -> `healthy`) and loopback boundary:
     ```bash
     curl -i http://127.0.0.1:8765/.well-known/oauth-protected-resource/mcp \
       -H "Host: mcp.directedideation.com"
     ```
     Confirm it returns `200` with `"resource": "https://mcp.directedideation.com/mcp"`, and that `-H "Host: mcp-staging.directedideation.com"` returns `400`.

7. **Switch Nginx TLS Server Block to `mcp.directedideation.com`:**
   - Swap the active Nginx config to serve `server_name mcp.directedideation.com;` with `/etc/letsencrypt/live/mcp.directedideation.com/{fullchain,privkey}.pem` (keeping the `default_server` `ssl_reject_handshake on;`, `60r/m` rate limit, `64k` body limit, and `proxy_pass http://127.0.0.1:8765;`).
   - Run `sudo nginx -t && sudo systemctl reload nginx`.

8. **External Smoke Test & Client Re-auth:**
   - From an external machine, verify:
     - `curl -i https://mcp.directedideation.com/.well-known/oauth-protected-resource/mcp` -> `200 OK`
     - `curl -i -X POST https://mcp.directedideation.com/mcp` -> `401 Unauthorized`
     - Unknown SNI / wrong `Host` header rejected.
   - Update the MCP client URL to `https://mcp.directedideation.com/mcp`, re-authenticate through WorkOS (to obtain a token with `aud: https://mcp.directedideation.com/mcp`), and invoke `ping` and `get_directed_ideation_method`.

### Instant Rollback (If Anything Fails)
- Restore the previous Nginx config and reload Nginx.
- Re-tag `directed-ideation-staging-mcp:rollback` to `directed-ideation-staging-mcp:local` and run `docker compose -p di-staging up -d --no-build --pull never --force-recreate` with `STAGING_MCP_HOST=mcp-staging.directedideation.com`.
